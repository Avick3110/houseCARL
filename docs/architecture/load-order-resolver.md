# The load-order resolver

## What it is
`LoadOrderResolver` is a held structural index over the active order — winner and override
depth per FormKey, plus the ordered touching list for the keys more than one plugin touches —
with no record bodies and no plugin file handles at rest. The service that owns its lifecycle is
[`load-order-service.md`](load-order-service.md).

## Contracts

### The index
- The resolver holds no plugin file handles at rest, because a Windows mmap overlay opened without `FILE_SHARE_DELETE` locks its file against delete, rename and overwrite — exactly what MO2, xEdit and Explorer need to do.
- The build enumerates every plugin one at a time, low to high priority: open, enumerate, dispose, so at most one plugin handle is open at any instant.
- `Index` carries every FormKey; `Overriders` carries multi-override keys only, because a singleton's sole overrider IS its winner.
- The order is INJECTED: override counts, depths and containment are order-independent, and winner identity is only as correct as the path list handed to `Build`.
- One build is one immutable `IndexSnapshot`, swapped in as a single volatile reference write, so a reader outside the service's gate can never see a new index beside old overriders.
- A logical operation captures that snapshot ONCE (`Capture`) and answers every question off the captured view, so no one response mixes two adjacent builds.
- Each `Index` entry also carries a one-byte code for the winning copy's record class, interned while the build already holds every record (`IndexTypes`), so it costs no read and nothing is hand-written. The code stands for the class and for its seek type (`WriteEngine.SeekTypeFor`: the flat group's getter, so every Global variant shares `IGlobalGetter`). The entry is packed as `(ushort winner, ushort count, byte type)`, the same 40 bytes as before; `Build` refuses an order past 65,535 plugins, far above the engine's 254 full plus 4,096 light. Codes run 0 to 254: Mutagen models about 133 Skyrim classes, and interning a 256th class throws rather than reuse `Mixed` or wrap.
- A key whose providers differ in class carries `IndexTypes.Mixed`, and each provider's own class code sits in `MixedTypes`, aligned with `Overriders`. That includes providers that share a seek type (a GlobalFloat overridden as a GlobalShort), so every provider's class is kept, not only the winner's.
- A partial form does not win (#1209): the winner slot is the newest provider whose copy is not partial in effect, by one predicate, `PartialInEffect`, read off the record header and its containing record during the walk (no subrecord, so it adds no parse that could exclude a plugin). A copy is partial when it carries flag 0x4000, is a CELL, WRLD or DIAL, and is an override (the defining plugin's own record never is). As in xEdit, a temporary exterior cell (one a worldspace holds, without the Persistent flag) is never partial, whatever subrecords its copy carries; an interior cell is told by where it sits too, not by a stray grid. A master-flagged plugin's partial is skipped like any other, and a partial WRLD is skipped whole, although the engine still loads its NAM0/NAM9. Membership is unchanged: the partial's plugin stays in `Overriders`, `TouchingPlugins` and `override_depth`, and a read naming it returns its own copy. A key whose every copy is partial (its definer not in the order) keeps the newest as its winner. Readers that need the winner's position (`WinnerClass`, `ConflictTree.WinnerAt`, the tree fold and its `(winner)` label) read it off the index, never "the last provider": a key a partial form tops keeps its winner's position among the providers in `Displaced` (so a plugin holding one key full, then partial, wins on its full copy), and every other key's winner is its last provider; the 40-byte entry is unchanged. The tree fold still walks each provider plugin once per chunk: a row's partial copies above its winner are read when their plugin is walked and only their materialised fields are held, no body, until the winner arrives, so the winner is still the row's baseline (read-engine.md).
- Every build trims the winner index (`BuildIndex`); the heap is settled once, in the constructor after the FIRST build only, because on a `RefreshIfStale` re-index the old snapshot is still live and would be copied. Measured in #728, landed in #802.

### Exclusion
- A plugin that will not OPEN, or that holds a record Mutagen cannot PARSE, is excluded whole-plugin and the reason is surfaced (`LoadFailures`, `ExcludedPlugins`), never skipped silently.
- Exclusion is atomic per plugin: keys go into a per-plugin buffer and merge only if the whole plugin enumerated, so a plugin that throws part-way never half-populates the index.
- A plugin excluded for a PARSE failure still names the keys it defines or overrides: `RecordHeaderKeys` walks its record headers (type and FormID, no subrecord parsed) where it is excluded, into the snapshot's `ExcludedTouches`, with each plugin's load position. Every lane asks that one fact through `IndexView.ExcludedTouchers` / `ExcludedTouchRefusal` and never re-derives it; a key counts only where an excluded plugin loads after the key's indexed winner (or there is none), since a later readable plugin already wins over it. Reads: a row on such a key carries the `OrderDegraded.TouchNote` note (text `note:`, json `excluded_note`, dense and `to_file=` as an `excluded_note` entry in `editorid_notes`) on the summary, fields, tree and delta forms, except a delta whose subject is the excluded plugin's own file; the walk's node line and resolve_names (text and json `error`) give one unresolved sentence for every unresolved link, naming the excluded plugin for a key it defines or injects. Writes: default-lane apply and forward (both lanes) refuse such a target, since a patch built without that plugin's version could undo its change (or, for a key with no indexed winner, since it has no readable version), and CopyFrom refuses it as a winner source; in-place apply does not refuse, since it edits the target's own record; the compaction and merge referencer pass lists a parse-excluded plugin as unread when its header names a plugin being renumbered as a master (only then can it reference or override one), so their in-place lanes refuse; it adds nothing to the unscanned record count. The errors check labels a reference into such a key as into the excluded plugin and counts those apart in its headline and `counts_only=` tally. An order with no parse-excluded plugin has an empty fact and answers as before. A file whose headers cannot be walked either, or one that could not be opened at all, adds nothing, and its reason says reads of what it touches are not marked. Not marked: `override_depth` and `conflicts_only=`, the chain and info_order forms, `group_by=winner` counts, the dialogue and facegen checks, the MGEF trace, the SkyPatcher replay and the containment walk. Not refused: create, remove and `housecarl_copy`, and a parent (CELL, WRLD, DIAL) an override copies in with its target is not asked (#1247).
- `Unopenable` is the subset of `Excluded` whose file could not be opened at all, kept as its own set rather than derived from the reason string, because a message is display prose and membership is a fact.
- A master set retains excluded-but-openable plugins on purpose — a clean plugin can override a record whose origin master is excluded, and that master must still appear in the patch header — and skips the unopenable ones, recording each name so a serialize failure can be attributed.
- An ACTIVE baseline master (Skyrim.esm / Update.esm) that cannot be opened refuses every write, thrown from the master-set builders, the single point every write lane funnels through.
- A plugin that opened at index time but not now is `PluginUnreadableException`; one that opened but could not be walked to the end is `PluginUnscannableException`. Two faults, worded differently, both reported as whole-plugin coverage gaps. `WinnerRecordsOfType` given a collector collects either one and walks on to the next plugin; without one it throws it. Partway through a plugin only a parse fault (`RecordParseFault`) is collected; anything else, a cancellation above all, goes on up.

### Identity and freshness
- The epoch fingerprint is derived from every plugin's filename, RESOLVED PATH and freshness stamp in priority order, plus the names of the plugins the build excluded; two builds over an unchanged order that indexed the same set fingerprint identically.
- `EpochFormat` tags the formula, so an epoch a different formula wrote is not comparable at all — a different sentence from "your load order changed".
- Two known approximations the epoch shares with the freshness baseline: an unstattable-but-openable file collapses to `FileStamp.Absent`, and an edit that changes neither the last-write time nor the length is invisible to both.
- Every freshness check compares stamps by VALUE, never by wall-clock order: MO2's "Restore Backup" writes an OLDER mtime, and a same-mtime rewrite that changes length is invisible to the mtime term alone.
- `RefreshIfStale` handles content edits to existing plugins; a changed plugin SET is a new order and the caller rebuilds.
- Every baseline is statted BEFORE the read it baselines, so a write landing during the read shows up on the next check rather than being absorbed into the baseline.
- Freshness never fires between tool calls — no watcher, no loop — so an actively re-sorting user cannot make the server thrash.
- The reverse-reference index is held on the RESOLVER, not the snapshot, and carried over when a rebuilt resolver replaces one (`AdoptReverseIndexFrom`); its partitions are keyed on (path, last-write, length), so only the plugins this order added or changed are walked; a rewrite that keeps the time but not the length rebuilds its partition.

### Fetching one record
- Every in-order fetch is typed by the index, through one door: `SeekBody` for one record and `CollectRecords` for a gather, which groups the wanted keys by the seek type their copy in that plugin carries and walks each type's groups once. No caller passes a type. On Mutagen 0.54.4 every pass over a top-level group copies the whole group, so an untyped seek of a Skyrim.esm armor addon cost 1.5 s and 1.37 GB; typed it is about 1 ms (#1158).
- Seek types that share top-level groups (cells, worldspaces and the references and navmeshes in them) share one read of each group in a gather: `CollectRecords` reads the group once and walks it once per type. Which groups hold which type is `MutagenGroups`, derived from Mutagen's getter interfaces by containment (never form links); the base record interface, held by every group, maps to null and walks flat. `CostCounters.GroupReads` counts reads per (plugin, group): every in-order walk goes through the resolver's `Walk`, which walks and counts each group of its seek type that the plugin has, or counts `*flat` for a flat walk or a type with no group map; a gather's shared-group read counts the one group it read. A group the plugin lacks is not counted on either lane: Mutagen stands in an empty, writable group for it, and `MutagenGroups.Present` skips it. A gather also skips a group once every wanted type was found. The index builds, the off-order reads and the check sweeps are not counted.
- A copy the build says a plugin does not hold is absent with no read. The flat walk is kept only for a key the build did not see, or a typed walk that misses because the plugin was rewritten keeping its size and last-write time, the one change the mid-call check cannot see; the next call's freshness check rebuilds. `CostCounters.TypedSeeks` and `TypedCollectPasses` count only fetches the typed walk answered, so a fallback shows as a gap.
- `IndexView.WinnerClassOf` answers the winning record's class off the index with no body read: the write pre-flight's link-target check and the facegen check's "not an NPC" row read it.
- Off-order files are not indexed, so their lanes still walk the file themselves.

### A plugin changed mid-call (ruling F)
- Each build keeps the stamp (last-write + length) it read every plugin at (`BuiltStamps`). Every open of an active plugin in a call (the session, the scan streams, the reverse-index partition build) first compares the file's stamp once against its build; a mismatch throws `LoadOrderChangedMidCallException`, one sentence naming the plugin. A file a call opens by path (`MidCallChange.Open`: a write's target, merge donors, a compact source, masters) is looked up in the call's build first and checked against its build stamp; only a file outside the order is pinned at first sight, and every later open must match.
- The tool guard holds one mark per call (`MidCallChange.Begin`). The first change found is kept on it, so a lane that folds the throw into a row or a partial answer still returns the refusal. `BodyGather.WalkOnce`, `CollectRecords`' open and the reverse-index partition build let the refusal through rather than naming the plugin unreadable.
- An answer read off the index alone opens no plugin (the dialogue check's target types, `WinnerClassOf`). So a captured view marks each plugin it answers a fact about (`ResolveWinner`, `TouchingPlugins`, `Touches`, `WinnerClassOf`, `IsLightFlagged`, `IsMasterBlock`), and before a call answers, the guard re-stats those plugins and every pinned file. Re-statting the whole order instead cost a single read 14 ms on ARR (17 to 31 ms).
- A write re-runs that sweep, plus every plugin the call opened, just before `CommitStagedPatch` swaps the file in, so a file another program saved since the write read it refuses the write and keeps the other program's bytes. The call's own output is exempt after its commit. A call that committed answers what it wrote; a change found after a commit refuses the rest in one sentence naming the files already written ("after houseCARL had written A, B; the rest was not done. Check those files before rerunning.").
- Not covered: `.seq`, asset and INI writes, which write no plugin; the commit sweep needs the guard's mark, so an engine call made without it gets the per-open checks only. A rewrite that keeps both the length and the last-write time is invisible here, as it is to `RefreshIfStale` and the epoch. The checks are a stat then an open, so a save landing between the two is read unseen; once the file is open, Windows blocks the save.
- A profile switch mid-call changes no plugin file: the call answers whole off the order it began on, and the next call follows the new profile.

### Sessions and writes
- A per-call `OverlaySession` opens each plugin the call touches AT MOST ONCE and disposes every one when the call returns; the write path takes its master set and its link cache from that same session.
- A write never leaves a mapped handle on the file it is about to serialize: `AllMastersExcept` skips the target's INDEX rather than filtering the returned list, and `ReleaseOverlay` closes a target overlay a winner fetch opened.

### The service's answers
- A body the index says exists but the plugin cannot yield is a NAMED inconsistency, never a silent null (`FetchRecord`); `GetRecord` answers null for a plugin absent from the order, excluded this build, or in the order but not defining the FormKey — a caller that must tell those apart asks `ContainsPlugin` too.
- A refusal naming a plugin the order does not contain carries the INJECTED explanation of why when there is one, and the did-you-mean otherwise. The resolver is built from a bare ordered path list and knows nothing of MO2, so the explanation is injected by the service.
- `OpenOverlay` is the single overlay-open choke point; it, and every other open, takes its read parameters from `PluginTextEncoding.ReadFor`, which sets the language and where the plugin's string tables are read from.
- The game language (#1212) and the string-table winners are `GameLanguage.Read`, run by the service in the same step as each order build (first build, a changed order, and a profile touch that keeps the order), off that build's own profile read. The language is `[General] sLanguage` from the INI the game reads (`GameIni`: the profile's own INIs when its settings.ini sets `LocalSettings=true`, `Documents\My Games\Skyrim Special Edition` when it sets false, the profile's when there is no flag and it has a Skyrim.ini; `SkyrimCustom.ini` over `Skyrim.ini`, key by key; no value is English). The base archive list (`ArchiveDiscovery`) reads the same INI. The game INIs are not stamped: an sLanguage edit alone is read on the next profile touch (#1239). `HOUSECARL_MY_GAMES` replaces the My Games folder; the tests set it so they never read the machine's own.
- A plugin's string tables come from their MO2 winners, by the asset layer's precedence (#1075 is one case): per table file, a loose `Strings\` copy wins (overwrite, then enabled mods by priority, then the game Data), else the highest-ranked loaded archive Mutagen opens for the plugin: one the INI lists, in any layer, or one named for it by Mutagen's rule (its name, or its name before the last " - "). An archive named for another plugin and not INI-listed is not used. Mutagen reads a plugin's tables from one loose folder and one archive folder, so kinds that win from two loose folders, or from archives in two folders, are not a winner: Skyrim.esm's split is refused, and another plugin keeps the old rule below. The winners apply only to the copy the order serves (paths compared as full paths, however spelled); any other copy (an off-order read of a disabled mod's file) and a plugin no layer carries tables for keep the old rule: beside it when its folder has them (in the game's language; any for English), else the game Data. Mutagen itself takes the INI-listed archives from My Games' Skyrim.ini, never the profile's or SkyrimCustom.ini (#1237), so where those differ an INI-listed winner in a folder can read blank. The read, the language refusal and the in-place census (`LocalizedStrings.Assess`: the order's language only, the loose winner before the plugin's own folder, `ArchiveHomeFor`) all answer from `InstanceText.WinnersFor`. Only the game language's tables are read, as the game does: a mod shipping only English tables reads no name on a German install, and the census calls that plugin's text not found.
- `ReadFor` sets Mutagen's `TargetLanguage` (left unset for English, so the language Mutagen selects for an English read is unchanged) and decodes non-UTF-8 text with Mutagen's own code page for the language (`MutagenEncoding.GetEncoding`, its code-page half), keeping #740's UTF-8-first read; every language Mutagen gives no code page (Chinese, Korean, Thai and the rest it answers with UTF-8) decodes it as Windows-1252, which takes every byte, so a legacy file's bytes are written back as read, while an ASCII-only file written in place takes UTF-8, that language's text. A plugin's lane is set by its own bytes, recorded per language; a localized plugin's string tables' decode counts toward it only in English, which keeps an English write the bytes it was.
- An `sLanguage` that names no game language, or a non-English language in which Skyrim.esm lacks any of its three tables, throws `GameLanguageRefusedException` from `GameLanguage.Read`, before the build or refresh publishes anything. The sentence names the missing kinds, an archive that carries a missing kind but is named for another plugin, a split of its kinds across folders, and the archive-list warning when the list could not be read. The old build is kept and every call that refreshes the order answers the sentence until the profile changes; a call that does not refresh (a write holds the gate, or an asset lane that does not refresh the order) answers from the old build, and after a refused first build there is none, so such a call reads English. English is never refused.
- The service binds its current `InstanceText` to the tool call (`GameLanguage.Begin` in `Guard.Tool`, `Bind` where the service hands out its resolver or roots), and every open and write in the call reads it from there once; nothing looks a language up by path, so an output outside the instance writes in the instance's language. Outside a bound call (a direct engine caller) the answer is `InstanceText.English`, the pre-#1212 read.
- Light and master-block are separate per-plugin facts read off the same open header: an esp-fe is light in the FormID space and a regular plugin in the order.
- `RecordsIn` walks its plugins in load order, each once, and yields a FormKey several of them touch only from the highest-loading one, so its answer does not depend on the order the names were passed in. An empty scope is the whole order minus excluded plugins; a name not in the order is refused by name, off the caller's captured snapshot; a scoped plugin that no longer opens throws `PluginUnreadableException`, ending the stream.
- The first active plugin whose KIND could not be read is kept as a position, not a flag: a runtime FormID landing at or after it is refused, one landing before it answers normally.

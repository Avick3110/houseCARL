# The load-order service

## What it is
`LoadOrderService` owns the resolver's lifecycle: it derives the roots, builds lazily, keeps the
build fresh, and is the one place the tools reach the core engines. The index it builds is
[`load-order-resolver.md`](load-order-resolver.md). Where the roots and the profile files come from is
`docs/architecture/mo2-instance.md`; that note owns the profile files, the priority model and
the config file.

## Contracts

### Sessions and writes
- `_writeGate` serializes the whole resolve, stage and commit of every plugin write; `SetInstance` takes it too, so an instance switch cannot tear a write in flight. Where both gates are held the order is `_writeGate` then `_gate`. The `Resolver` and `Assets` getters are the one exception: they take `_gate` first and only try `_writeGate` with `Monitor.TryEnter`, never waiting on it, so the reverse order never turns into a wait. The output area's `FolderAllocationGate` serializes only the check-then-create of a fresh houseCARL mod folder (`ResolvePatchModFolder`, `ResolveOutputPath` and `CreatePlugin`; never a caller-named `out_path=` folder), and is taken last, after either gate or inside one, and nothing takes `_gate` while holding it. The active plugin names that stem check uses are read before it is taken, from the same `_gate` hold as the roots, so a load-order build never runs under it and a stem is never checked against one instance's plugins and another's mods folder. The stretches under it still parse the profile for the shadow sweep (`CreatePlugin`, and `ResolveOutputPath`'s `UniqueStem`), but reads never stall behind that: nothing waits on it while holding `_gate`, and every write that takes it holds `_writeGate` (`ResolveOutputPath`'s callers, `CreatePlugin`, `WriteSeq`, `CompactPlugin`), so a write only ever waits on another write or on a gate-free rider (compile, decompile, bsa), which allocates with `writes: null` and parses nothing; `nif_set` allocates the same way but holds `_writeGate` while it does, so it is one of the writes. A `ResolveOutputPath` caller without `_writeGate` would break this. `UniqueStem`, `StemCollision`, `ReadCompositionForShadow` and `ActivePluginBasenames` are static, so nothing under the lock can reach head state.
- A read-path profile or record refresh is DEFERRED while another thread's write holds `_writeGate` — probed with `TryEnter`, never blocking — because a rebuild transiently maps every plugin including the one the write is serializing and dispose-swaps the resolver that write captured; a skipped refresh serves the last good snapshot and re-checks next call. The asset content check (archive bytes and warmed loose folders) is not deferred: it runs during another call's write too, since that write reads its own frozen copy of the file view (#1128's asset half). On the writer's own thread `TryEnter` re-enters: outside a call a getter called mid-write still refreshes (#1032); inside a call only the write's first read in the gate does (below).
- Lock order is `_gate` then `_classParentsLock`. Nothing pins it.

### The per-call context
- Every tool call opens one `CallContext` (`src/housecarl-mcp/CallContext.cs`), held by the `ToolCall` that `Guard` opens around the body, reached by the service's getters through an `AsyncLocal`. Outside a call (a test or probe calling the service directly) there is none, and every getter refreshes as described above.
- **Records, checked once at the call's first record read** (concern 2's (B) and (R1), DECISIONS 2026-11-04 (12)). The first `Resolver` read in a call runs the freshness check above, then the context holds the pin (`ViewPin`, whose view carries the epoch) and the four roots, and the call's language scope binds the build's language then; the call's first file read, whose profile check can re-read the language, can rebind it. Every later `CapturePin`, `CaptureView`, `CaptureRoots` and `ConfiguredRoots` read in the call returns those with no refresh, as do the held capture fields, and a profile or plugin-list change shows at the next call. Every `Resolver` read in a call, the first included, returns the pin's resolver, a frozen copy (`LoadOrderResolver.Frozen()`): another call's in-place rebuild moves the live resolver, not the copy, so a lane's own `Resolver.Capture()` reads the pin's build. A plugin's bytes changing under the pin is still the mark's refusal. Once a call holds files and no pin, `CaptureRoots`, `ConfiguredRoots` and `CaptureAssets().Roots` return the roots of its first file view.
- **Files, checked once at the call's first file read.** A records-only call builds no file view. The first `Assets` read runs the profile check and the archive and watched-folder check (a `CapturePinAnd…` hold's asset capture runs only the archive and watched-folder check), then the context holds the asset build as a frozen copy (`AssetResolver.Frozen()`), with the live build it came from and the warnings, archives, enabled mods and profile name read beside it; every later file read in the call returns those, even after another call has refreshed or dropped that build.
- **The head's own reads answer the call's roots.** Inside a call that holds a view, `ModsRootOrNull`, `PapyrusSourceImportDirs`' data folder, `StatusData` (roots, profile name and composition) and the plugin-absence explainer (roots and composition) read the call's roots and the profile read its build kept, not the service's current ones, so a switch another call followed mid-call does not reach them. Outside a call, or when the build kept no profile read, the composition is read fresh.
- **A profile change between the two refuses the call** ((P1)). The first view taken, records or files, stamps the call with the build it was taken against (`CallBuild`: the roots, the order as the resolver object, the profile read and the profile name). The check compares only the roots and the order, so a mod-list change that keeps the plugin paths passes it. If the first view of the other kind finds either has moved, the call refuses whole with one sentence, "the load order changed while this call was running … Retry the call.", the words the epoch seams use; once a write has committed, the sentence instead names the files written, and any plugin the mark found changed on disk, and says the rest was not done, as the mark's does. `Guard` reads the refusal off the context, so a lane that folds the throw into a row still refuses.
- **A write takes its view once, inside the write gate, and finishes on it** (#992; DECISIONS 2026-11-04 (20), "Finish on the pin's view"). On a thread that holds `_writeGate`, the call's first read in the gate is not served: it refreshes as it does outside a call, and the context adopts what it took (keeping its pin when the build and its profile read have not moved), so a write decides against an index that includes every write committed before it. That read is the lane head's pin, or, for an asset-only write (place, `nif_set`), its first file read; it marks the write's view taken. Every later getter read in the call serves that view and never refreshes the profile or the order: the post-write carries, the SEQ gate, the `.seq` staleness note and the voice and script checks all judge the build the write was decided on, so a mod switched off or a profile switch after the pin is seen by the next call, not this one. A post-commit file read with no file view held takes the build the in-gate pin names: the asset build reads the profile read that order was built from, not the profile as it is on disk now (it still runs the content check, once). Only a call's first view of each kind is checked against its stamp: an in-gate re-pin adopts a profile switch without refusing, roots and order included, since a pin sets the build each time, and when it moves the build the files the call held from before the gate are let go, so its post-commit files follow the pin; an in-gate file read once the call holds files adopts the new profile's files without refusing, but with no pin held the call's roots stay its first file view's, since a file view sets the build only when none is held. A call takes the write gate once, so "first read in the gate" is once per call.
- The context holds nothing past its call. The mid-call mark and the game-language scope stay their own `AsyncLocal`s beside it in `ToolCall`. Lanes reach the load order through the getters, which serve the call's frozen views (plan step 9, #992).

### The shared head door
- `ILoadOrderHost`, in `src/housecarl-mcp/LoadOrderHost.cs` with the `AssetCapture` it returns, is how an area reaches the head members areas share. It carries the head members the area split assigned to it from the start (`Resolver`, `Assets`, `CaptureRoots()`, `CaptureAssets()`, `WriteGate`, `Rulebook`), plus any head member two areas take (`CapturePinAndAssets`, `CapturePinAndRoots`, `Types`, `ConfiguredRoots()`, `InPlaceConsent`), and each only once some area actually takes it through the door: today `Resolver`, `Assets`, `CaptureRoots()`, `CaptureAssets()`, `CapturePinAndAssets(afterPin)`, `CapturePinAndRoots(afterPin)`, `WriteGate`, `Types`, `Rulebook`, `ConfiguredRoots()`, `InPlaceConsent` and `ServingCopyMoved`. The head implements each member once, explicitly, next to what it wraps; rows relayed from other areas sit together in one block of the head.
- `Resolver` and `Assets` are the head's own getters, with their freshness and lock behaviour above. `Assets` is the asset resolver, for a core check that captures it itself per seed: inside a call, the call's frozen copy; outside one, the live build.
- `CaptureRoots()` returns `Mo2Roots` (profile, data, mods and overwrite folders) from one `_gate` hold: it derives the roots first and throws whatever derivation throws. It takes no configured check: an unconfigured service yields four empty roots, and explicit mode always yields an empty overwrite root. Callers that need a configured instance have already gone through `Resolver` in the same call.
- `CaptureAssets()` takes one `_gate` hold: it captures the asset build through the `Assets` getter, which checks the service is configured and derives the roots first, then reads the warnings, profile name, the four roots (carried as one `Mo2Roots`), active archives and enabled mods of that same build. The caller works on the capture outside the hold.
- `CapturePinAndAssets(afterPin)` is the one-hold pin-plus-assets capture three areas take (the SkyPatcher layer scan, the facegen and script sweeps, and the read area's SkyPatcher overlay source and pole): one `_gate` hold pins the index view with its resolver, runs `afterPin` (a test seam, null in the product), then captures the asset build without a second profile refresh, so a profile switch cannot split the pin from the assets.
- `CapturePinAndRoots(afterPin)` is the same hold with the four roots in place of the asset build, for the lanes that need the roots but no asset build (the read area's pole lanes and the errors sweep): the pin, `afterPin`, then the roots, so a profile switch cannot split the pin from the roots.
- `CapturePinRootsAndAssets(afterPin)` is on `ICheckHost`, not the door, since only the checks area takes it. It is the same hold with the four roots and the asset resolver (in a call, the call's frozen copy; outside one, the live build), taken without a profile refresh, for the dialogue sweep, whose validator captures its asset build per seed and so needs the resolver rather than one `AssetCapture`.
- `WriteGate` is the same object as `_writeGate`, so the lock order above holds through it: take the write gate first, then capture.
- `Types` is the service's `TypeLookup` (a `type=` string to its getter types), built from the corpus on first use and kept for the service's life, so a `CorpusRulebook.CorpusPath` set before a service's first type resolution governs that service. It is never process-wide. The read, check, write and asset lanes resolve types through it.
- `Rulebook` is the service's `CorpusRulebook` (corpus.json), loaded on first use from the `CorpusPath` set then; concurrent first calls publish one instance, and a failed load is not kept. The read area's scan takes it to judge a `where=` quantifier's shape; the write lanes use the same instance.
- `ConfiguredRoots()` is one `_gate` hold that runs the configured check and returns the four roots and the built resolver's plugin names together, so a stem is never checked against one instance's plugins and another's mods folder. Output and the write lanes take it.
- `InPlaceConsent` is the one `InPlaceConsent` the head builds over its config store, for the write lanes' and `nif_set`'s in-place handshake ([`write-path.md`](write-path.md)).
- Each area's own interface extends `ILoadOrderHost` and carries the rest: the head members only that area takes, plus rows relayed from other areas. The first is `IAssetHost`, in `src/housecarl-mcp/AssetLayers.cs`; the second is `ICheckHost`, in `src/housecarl-mcp/RecordChecks.cs`; the third is `IReadHost`, at the top of `src/housecarl-mcp/RecordReads.cs`; the fourth is `IOutputHost`, at the top of `src/housecarl-mcp/OutputLocations.cs`, which has no members beyond the shared door. The fifth is `IWriteHost`, at the top of `src/housecarl-mcp/RecordWrites.cs` (`OpenWriteFormIdDoor()`). Those five areas are their own classes, `AssetLayers`, `RecordChecks`, `RecordReads`, `OutputLocations` and `RecordWrites`, each built by the head over itself (assets and writes also over the output instance). The two instance edges between classes are assets and writes each holding the `OutputLocations` instance its constructor takes; the one relay between two classes is `IReadHost.OpenSkyPatcherReplay`, which the head passes to `AssetLayers`: it opens the replay over an asset capture the caller took in its pin's hold (`CapturePinAndAssets`), and reads reaches it through the head rather than holding the assets instance. An area otherwise calls another class's statics directly, as checks and assets call `RecordReads.OpenDialogueFold` and `RecordReads.UnresolvedFormId`.

### The service's answers
- The index build is lazy, so startup and `tools/list` are instant, and it is serialized on one gate because the server dispatches tool calls concurrently.
- A refresh that lands in MO2's own profile-rewrite window keeps the snapshot already built and does NOT advance the baseline, so the next call re-checks and follows the new profile.
- A profile change that could not be RE-READ is remembered: the asset lane keeps answering and says so in its warnings, and the record lane refuses, because the record index IS the load order.
- A mid-write read that resolves no paths keeps the last good snapshot and does not advance the baseline, so the next call recovers once MO2 finishes writing.
- Every order build and every profile re-read that publishes (a changed order, or a touch that keeps it) first reads the game language and string-table winners (`GameLanguage.Read`, [`load-order-resolver.md`](load-order-resolver.md)) off that build's own profile read; a language refusal throws there, before anything is published, so the old snapshot and baseline stay and every call that refreshes the order answers the sentence until the profile changes. The service binds its current answer to each tool call where it hands out its resolver or roots.
- A profile switch publishes the new roots only together with the order read from them: when the new profile's read is held or empty, the old roots, resolver and ini stamp all stay, and the next call retries. So a pin and the roots taken beside it always describe one profile.
- Which copy serves each plugin is decided when the order is built and re-decided only when a profile file changes; `RefreshIfStale` stats only the paths the build resolved, so a same-name copy dropped into a higher-priority mod (or the serving copy removed) changes nothing it watches. The live check (`ServingCopyMoved`, #1196) walks only the enabled layers to the first hit (`Mo2LoadOrder.ServingCopy`), judges it with `OutputLocations.JudgeServed`, and inside a call judges against the call's roots and the profile read its build kept (outside a call, or with none kept, it parses the profile once per check, which a compact's referencers share), so a toggle or switch after the call's pin is the next call's: an in-place write finishes on its pin's copy, and `load_order_status filter=` judges the copy its pin indexed; it runs only in three places: every in-place write (apply, create, remove, forward, compact), a `records` read whose source names a mod and whose named copy now serves, and `load_order_status filter=` on an active plugin. One lookup on ARR costs about 5 ms (n=20, 0.6 to 21 ms) plus 1.8 ms for the profile parse, too slow for every plugin a call touches. When the live copy is the index's, nothing more runs; the full locate runs only on a refusal, to label the index's copy. When the current index already holds the live copy (a view pinned before another call refreshed), the call refuses with no rebuild. Otherwise the order is re-resolved through `ReResolve`, the profile-change path (deferred while another thread writes, like every read-path refresh, and on a write's own thread once it took its view in the gate put off to the next call, whose profile check re-reads the order); the write writes nothing and the read reads nothing, each refusing in one sentence naming both copies, and the rerun answers from the served copy. A read refuses rather than re-reads, because its pin was taken off the old build. When it could not refresh (another write holds the gate, the write's own view is taken, MO2 holds the profile files, or the profile read back empty), the refusal and the status `index:` line say which and when to run again; `ServingCopyReResolves` counts only published rebuilds. Still missed: a plain read with no write, mod-named read or status call in between answers from the old copy until a profile change or one of those calls rebuilds.
- The asset resolver is built only on an asset query, never forces the record index build, and is dropped whenever the active mod or archive SET changes. It is built off the profile read the current order was built from (its composition and archive discovery); with no order read yet it reads the profile itself. A first record build keeps an asset build made before it when a files-first call's re-read already set the order's paths, so that asset build can describe an earlier read of the profile than the order, until the next profile change.
- A record build that lands while an asset build was KEPT across a profile change drops that asset build instead of advancing the baseline past it, so the next asset call rebuilds rather than silently serving the old answer.

### Configuration modes
- INSTANCE, the product default: one MO2 instance folder, roots and active profile derived from `ModOrganizer.ini`, and a profile switch picked up on the next tool call.
- EXPLICIT, a dev override: the three roots are configured directly, no ini is read and no profile-switch watch runs.
- UNCONFIGURED: the server still boots and every tool returns the prompt for the MO2 path until `housecarl_set_mo2_instance` is called.
